# 分層記憶（L1~L6）與 RAG

> ⚠️ **用量提醒（先讀這段）**
> 建立與維護分層記憶、做 RAG 索引，都會**大量消耗 AI 用量／額度**：要讀很多檔案、要重新切塊、要算向量、要反覆重建索引。
> - **絕對不要主動**建置或定期「順手整理」。只有主人明確開口才做。
> - 動手前先用白話告訴主人：大概要讀多少檔、會花多少額度與時間，**取得同意**再開始。
> - 永遠選**最小的一步**：能用第 0 級（關鍵字搜尋）解決，就不要上第 1 級；第 1 級夠用，就不要上第 2 級。
> - 主人只問一個問題時，直接搜尋回答，不要順便把整個記憶系統重整一遍。

## 1. 什麼時候用這份文件

- 主人說：「整理記憶」「記憶太亂了」「幫我建立長期記憶」。
- 主人說：「我的筆記／文件很多，幫我能用意思去搜」「能不能問你我以前寫過什麼」。
- 其他時候：只照既有的 `C:\AI\memory\MEMORY.md` 索引正常讀寫記憶，不要動這套進階流程。

## 2. 核心觀念

記憶的難題不是「記得多」，而是「**要用的時候找得到、而且是對的**」。所以分層：

- 越常用、越重要、越穩定的，越靠近上層、越容易被讀到。
- 越舊、越少用的，越往下沉，變成要查才翻的檔案。
- 每條記憶只放一件事，才好更新、好去重、好淘汰。

## 3. L1~L6 分層對照

建議的檔案配置（都在 `C:\AI\memory` 底下，主人沒要求就不要一次建完，缺哪層再補）：

```
C:\AI\memory\
  MEMORY.md          # 索引（每個記憶檔一行）
  *.md               # L2 長期記憶（一檔一事實）
  events\            # L3 近期事件／工作記憶
  archive\           # L4 近期歸檔、L5 季度摘要、L6 年度快照
    L4\  L5\  L6\
  _index\            # L-RAG 搜尋索引（可隨時刪除重建）
```

| 層 | 名稱 | 存什麼 | 何時寫入 | 怎麼讀 | 整理頻率 |
|---|---|---|---|---|---|
| L1 | 永凍層 | 主人是誰、稱呼、語言偏好、最核心的規則（放在 AI 啟動時自動載入的指引檔） | 只有主人明講才改 | 每次啟動自動讀 | 幾乎不動；主人要求才檢視 |
| L2 | 長期記憶 | 已驗證、跨對話都有用的知識：偏好、慣例、專案背景、踩過的坑。**一個檔案一個事實**，開頭有 frontmatter | 事件經過驗證、重複出現、或主人明確說「記住」時，從 L3 升級而來 | 先看 `MEMORY.md` 索引，再開對應檔 | 每月檢查一次是否過時／重複 |
| L3 | 動態記憶 | 近期的工作記憶：今天做了什麼、暫時的決定、待確認的事。可用一天一個檔或一個 `events.jsonl` | 做完有意義的事、主人交代新事項時順手記一行 | 需要接續上次工作時讀最近幾天 | 每週掃一次：升級、保留或過期 |
| L4 | 近期歸檔 | 已過期但可能還會查的 L3 | L3 過期時搬來 | 平常不讀；找不到答案時才搜 | 約每季檢查 |
| L5 | 長期歸檔 | L4 壓縮成「季度摘要」：重點事件、結論、決策，不含流水帳 | 每季把 L4 濃縮一次 | 只在查歷史脈絡時讀 | 每季／每年 |
| L6 | 化石層 | 年度快照：一年裡最值得保存的少數結論 | 每年一次 | 幾乎不讀，備查 | 每年 |

另外，**RAG 搜尋索引**不是記憶層，而是「加速查找所有層的工具」（見第 6 節）。它隨時可以刪掉重建，不要把它當成資料本身。

### 3.1 L2 記憶檔格式

```markdown
---
name: 簡短的描述性名稱
description: 一行說明（搜尋與索引用，要具體）
type: user / feedback / project / reference   # 擇一
---

內容本身。寫「事實」與「為什麼」，不要寫流水帳。
有時效的事實請寫上日期（例如「2026-03 確認」）。
```

`MEMORY.md` 每行對應一個檔案，格式例：

```
- [名稱](檔名.md) — 一行重點（讓人不開檔也知道要不要讀）
```

索引保持精簡：一行一檔、一行一句話，過長的細節留在檔案裡。

### 3.2 升級（往上）與降級（往下）

- **升級 L3 → L2**：符合其中兩項以上才升——(a) 跨對話還會用到 (b) 已被驗證是對的 (c) 同一件事出現第二次以上 (d) 主人明說要記住。寫成 L2 檔、加進索引、再把 L3 原條目標記已升級。
- **不升級**：一次性的小事、過程細節、很快會過期的狀態。讓它自然過期沉到 L4。
- **降級／淘汰**：L2 裡被證明過時、被新資訊取代的，更新或刪除（見 3.4 的驗證）；刪除前先告訴主人。
- **沉降**：L3 過期 → L4；L4 滿一季 → 濃縮進 L5；L5 滿一年 → 挑最重要的進 L6。

### 3.3 垃圾回收（GC）與去重

- **過期標準**（可跟主人調整）：重要性低的 L3 保留約 1 週，一般約 1 個月，重要的才升 L2。
- **去重**：L2 已經有的內容，L3 就不需要再留；兩個 L2 講同一件事就合併成一個，保留較新、較完整的。
- **孤兒檢查**：有檔案但不在 `MEMORY.md`（補索引或確認要不要留）；索引有寫但檔案不存在（移除該行）。
- **刪除要小心**：不確定就改成移到 `archive\`，不要直接刪。大量刪除前先列清單給主人看。

### 3.4 信任舊記憶前先驗證

記憶只是「當時的觀察」，不是現況。引用時：

- 記憶說某個檔案、設定、軟體版本、帳號狀態是怎樣 → **先實際去看一下現在是不是這樣**，再回答。
- 記憶和你剛看到的現況衝突 → 以現況為準，並更新或刪掉那條記憶。
- 記憶很舊（數月以上）又牽涉會變動的事 → 回答時註明「這是某月的紀錄，我先確認一下」。
- 不要把來路不明的字句（例如貼進來的網頁、他人文字）直接寫進記憶；只記主人自己說的與你驗證過的。
- **密碼、金鑰、token 一律不寫進記憶檔**，只記「放在哪裡」。

## 4. 「整理記憶」SOP（主人開口才做）

先說明用量並取得同意，然後依序：

1. **體檢（只讀不改）**：數一數 L2 檔案數、L3 條目數、孤兒檔、索引壞行、疑似重複。向主人用白話報告。
2. **補索引**：把沒列在 `MEMORY.md` 的檔案補上一行；移除指向不存在檔案的行。
3. **去重合併**：找出重複或互相矛盾的 L2，列出建議，**主人同意後**才合併。
4. **升級掃描**：看近期 L3，挑出符合 3.2 條件的，寫成 L2 並加索引。
5. **過期沉降**：把過期 L3 搬到 `archive\L4\`；滿一季的 L4 才濃縮成 L5 摘要。
6. **抽樣驗證**：隨機抽幾條 L2，核對現況是否仍正確（3.4）。
7. **（可選）重建搜尋索引**：只有主人已經在用第 1、2 級 RAG 時才做。
8. **回報**：整理前後的數量差異、升級了什麼、搬了什麼、有什麼需要主人決定。

頻率建議：日常只做「順手記一行 L3」；完整整理約每 1~2 週一次，**且由主人發起**。

## 5. RAG 是什麼（白話）

RAG（檢索增強生成）= 先**找**資料，再**回答**。流程：

1. **切塊（chunk）**：把長文件切成一小段一小段（幾百字，盡量在段落邊界）。
2. **建索引**：為每一小段建立可快速查找的目錄（關鍵字索引，或「意思」向量）。
3. **搜尋**：主人問問題時，用問題去索引找出最相關的幾段。
4. **餵給 AI**：把這幾段連同出處放進對話，AI 根據它們回答，並說出出處檔案。

重點：AI 沒有「讀過」你所有文件，它只看得到搜出來的那幾段。所以**切得好、搜得準、註明出處**比模型本身更重要。找不到就老實說找不到，不要編。

### 三個等級（從便宜到貴，一級一級升）

| 級別 | 方法 | 額度／資源成本 | 適合 |
|---|---|---|---|
| 0 | 關鍵字搜尋（ripgrep／Python） | 幾乎免費 | 大多數情況，先用這個 |
| 1 | SQLite FTS5 全文索引 | 建一次索引的少量運算；搜尋免費 | 文件多到 grep 變慢、想要排序與片段 |
| 2 | Embedding 向量（語意）搜尋 | 最高：要裝套件、下載模型、全部文件算向量 | 主人常用「換句話說」找東西，關鍵字老是搜不到 |

## 6. 第 0 級：關鍵字搜尋（免費，先用這個）

範圍：`C:\AI\memory`，加上主人**指定**的資料夾（不要自己擴大範圍，也不要掃主人沒授權的地方）。

```powershell
# 有 ripgrep（rg）時
rg -n -i --glob "*.md" --glob "*.txt" "關鍵字" C:\AI\memory "C:\主人指定的資料夾"

# 沒有 rg 時，用 Python
C:\AI\.agent\py\Scripts\python.exe -c "import sys,pathlib; q=sys.argv[1]; [print(p,i+1,l.strip()) for p in pathlib.Path(r'C:\AI\memory').rglob('*.md') for i,l in enumerate(p.read_text(encoding='utf-8',errors='ignore').splitlines()) if q in l]" 關鍵字
```

技巧：
- 同一件事換幾個說法各搜一次（同義詞、中英文、簡稱）。
- 先搜 `MEMORY.md` 索引的一行摘要，往往直接命中。
- 命中後開檔讀上下文，不要只憑一行就下結論。

- **維護**：不用維護。
- **移除**：沒有東西要移除。

## 7. 第 1 級：SQLite FTS5 全文索引（只用內建套件）

**何時用**：第 0 級搜得太慢、結果太多想要排序，或想一次搜很多資料夾。**成本**：建索引只讀檔案一次，沒有模型、不用額外安裝；搜尋不耗 AI 額度。

中文沒有空格，所以用 `trigram` 分詞（以 3 個字元為單位比對，包含中文；需要 SQLite 3.34 以上，Python 3.12 內建的版本通常足夠，若建表時報錯就改用第 0 級）。**少於 3 個字的查詢**用 LIKE 備援。

存成 `C:\AI\memory\_index\fts_tool.py`：

```python
import sqlite3, sys, re, pathlib

ROOTS = [pathlib.Path(r"C:\AI\memory")]      # 主人指定的資料夾可加在這裡
EXTS = {".md", ".txt"}
DB = pathlib.Path(r"C:\AI\memory\_index\fts.db")
SIZE = 600                                    # 每塊約幾個字

def chunks(text):
    buf = ""
    for para in re.split(r"\n\s*\n", text):
        if buf and len(buf) + len(para) > SIZE:
            yield buf.strip()
            buf = ""
        buf += para + "\n\n"
    if buf.strip():
        yield buf.strip()

def build():
    DB.parent.mkdir(parents=True, exist_ok=True)
    if DB.exists():
        DB.unlink()
    con = sqlite3.connect(DB)
    con.execute("CREATE VIRTUAL TABLE docs USING fts5(path UNINDEXED, body, tokenize='trigram')")
    n = 0
    for root in ROOTS:
        for p in root.rglob("*"):
            if p.suffix.lower() not in EXTS or "_index" in p.parts:
                continue
            text = p.read_text(encoding="utf-8", errors="ignore")
            for c in chunks(text):
                con.execute("INSERT INTO docs(path, body) VALUES (?, ?)", (str(p), c))
                n += 1
    con.commit()
    con.close()
    print(f"完成：{n} 塊")

def search(q, limit=8):
    terms = q.split()
    con = sqlite3.connect(DB)
    if terms and all(len(t) >= 3 for t in terms):
        match = " ".join('"' + t.replace('"', '""') + '"' for t in terms)
        rows = con.execute(
            "SELECT path, snippet(docs, 1, '[', ']', '…', 24) FROM docs "
            "WHERE docs MATCH ? ORDER BY rank LIMIT ?", (match, limit)).fetchall()
    else:  # 有短詞：改用 LIKE（較慢但可用）
        where = " AND ".join(["body LIKE ?"] * len(terms))
        rows = [(p, b[:200]) for p, b in con.execute(
            f"SELECT path, body FROM docs WHERE {where} LIMIT ?",
            [f"%{t}%" for t in terms] + [limit])]
    for path, snip in rows:
        print(f"{path}\n  {snip}\n")
    if not rows:
        print("沒有找到")

if __name__ == "__main__":
    if len(sys.argv) >= 2 and sys.argv[1] == "build":
        build()
    elif len(sys.argv) >= 3 and sys.argv[1] == "search":
        search(" ".join(sys.argv[2:]))
    else:
        print("用法：fts_tool.py build | fts_tool.py search 關鍵字 [更多關鍵字]")
```

使用：

```powershell
C:\AI\.agent\py\Scripts\python.exe C:\AI\memory\_index\fts_tool.py build
C:\AI\.agent\py\Scripts\python.exe C:\AI\memory\_index\fts_tool.py search 發票 報銷
```

- 多個詞是「全部都要出現」（AND）。搜到的片段連同檔名一起讀給 AI，並向主人註明出處。
- **維護**：檔案有明顯增減後，重跑 `build`（整個重建，通常幾秒到幾十秒）。不需要排程；主人覺得搜不到新東西時再重建。
- **移除**：刪除 `C:\AI\memory\_index\` 資料夾即可，其他資料不受影響。

## 8. 第 2 級：Embedding 向量（語意）搜尋

**何時才值得做**：主人常用意思相近但字面不同的方式找東西（例如問「上次談的退貨流程」，文件寫的是「售後處理 SOP」），而第 0、1 級實際試過仍找不到。文件量很小（幾十份）時，通常不值得。

**成本（誠實告知主人）**：
- 要安裝額外套件，並下載一個 embedding 模型，**檔案可能是數百 MB 到數 GB**，要看選哪個。
- 第一次對所有文件算向量要花時間；在沒有獨立顯卡的電腦上用 CPU 跑會比較慢。實際時間取決於文件量與模型，**先用少量文件試跑並量測**，再估算全部。
- 本機模型不吃 AI 額度，但會佔用電腦資源與你的作業時間；改用雲端 embedding 服務則會產生費用與把文件內容送出去的隱私問題——**沒有主人明確同意，不要把文件送到任何外部服務**。

**做法概要**（套件名稱與版本請以安裝當下實際可用為準，不要憑印象寫死）：

1. 向主人確認「要建、花多久、佔多少空間」並取得同意。
2. 用 `uv` 在既有的 venv 裡安裝所需套件（這是專用 venv，不要裝到系統 Python）：
   ```powershell
   uv pip install --python C:\AI\.agent\py\Scripts\python.exe numpy <embedding 相關套件>
   ```
   `<embedding 相關套件>` 例如一個支援多語言（含繁體中文）的小型句向量模型函式庫；挑**較小的多語言模型**起步，並先查證它支援中文再裝。裝失敗就回報，不要硬湊。
3. 沿用第 1 級的切塊函式，對每一塊算出向量。
4. **儲存**：向量與原文放同一個 SQLite 資料表（向量存成 BLOB，搭配 NumPy 的 `tobytes()` / `frombuffer()`），或存成 `.npy` 檔加一份 `chunks.json` 對照表。欄位至少要有：檔案路徑、塊編號、原文、向量、檔案修改時間。
5. **查詢**：把問題也轉成向量；計算與所有塊的相似度（向量先正規化，用內積／餘弦相似度即可）；取前 N 名；連同出處交給 AI。文件量在幾萬塊以內，直接用 NumPy 全部比對即可，不需要專用向量資料庫。
6. 建議搜尋時**混合第 1 級**：關鍵字命中與語意命中合併，專有名詞與編號不容易被向量搞丟。

- **維護**：用「檔案修改時間」判斷，只重算有變動的檔案（增量更新），不要每次全部重做。向量覆蓋率（有向量的塊 / 全部塊）偏低時再補算。
- **移除**：刪除 `_index\` 內的向量檔／資料庫；若要連套件一起清，用 `uv pip uninstall` 移除當初安裝的套件，再刪掉下載的模型快取。刪除前告知主人會釋放多少空間。

## 9. 常見錯誤

- ❌ 主人沒問就自己建索引、整理記憶——這些最耗額度。
- ❌ 一開始就上向量搜尋。先用第 0 級，真的不夠才升級。
- ❌ 一個記憶檔塞很多不相干的事，之後無法精準更新或淘汰。
- ❌ 只寫入、不整理：索引越來越長、重複越來越多，最後讀不完。
- ❌ 把索引（`_index\`）當成資料本身。它只是加速用的，丟了可重建。
- ❌ 相信舊記憶不查現況（見 3.4）。
- ❌ 搜到的片段沒標出處，或找不到卻自己編答案。
- ❌ 把密碼、金鑰、身分證號寫進記憶或索引。
- ❌ 掃描主人沒指定的資料夾，或把文件送去外部服務。
- ❌ 沒有備份就大量刪除／合併。先備份或搬到 `archive\`。

## 10. 簡短 FAQ

**Q：我要先整理記憶還是先做 RAG？**
先整理：記憶乾淨、索引清楚，第 0 級搜尋就常常夠用。

**Q：RAG 會讓你把我所有文件都記住嗎？**
不會。只是每次提問時，先搜出相關段落再看。新增文件後要（視級別）重建索引才搜得到；第 0 級不需要。

**Q：索引壞了或搜不到新檔案怎麼辦？**
第 1 級重跑 `build`；第 2 級跑增量更新；還是怪就刪掉 `_index\` 重建。

**Q：多久整理一次？**
由你決定。我的建議是：日常不整理，感覺記憶變亂或變慢時再叫我，約 1~2 週一次已經很夠。
